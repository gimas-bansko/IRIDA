## Въведение

В реалната разработка на софтуер приложенията често обменят данни с други системи чрез уеб услуги. За да откриваме проблеми и да проверяваме дали дадена услуга работи правилно, трябва да умеем да изпращаме HTTP заявки, да разчитаме отговорите им и да свързваме действията с CRUD операциите върху данни.

В този практикум ще използваме конзолен HTTP клиент и публичния тестов REST API **JSONPlaceholder**. Това е безопасна среда за упражнения: заявките за промяна симулират работа, без да променят реални потребителски данни.

## След този урок ще можете да...

- изпращате `GET`, `POST`, `PUT` и `DELETE` заявки към REST API чрез конзола;
- разчитате URL адрес, HTTP метод, request headers, JSON тяло, статус код и JSON отговор;
- свързвате HTTP методите с CRUD операциите — Create, Read, Update и Delete;
- анализирате отговори `401`, `404` и `500`, като предлагате вероятна причина и следваща стъпка за проверка.

# 1. Основни понятия

## 1.1. Клиент, сървър и API

**Клиент** е програма, която изпраща заявка за данни или услуга. Това може да бъде браузър, мобилно приложение, конзолен инструмент или друга сървърна програма.

**Сървър** е програма или компютърна система, която приема заявките, обработва ги и изпраща отговор.

**API** (_Application Programming Interface_) е набор от правила, чрез които програми обменят данни и функционалности. В уеб разработката API често се използва през HTTP.

**REST API** е API, организиран около ресурси. Ресурс може да бъде потребител, публикация, коментар, продукт или поръчка. Всеки ресурс има адрес — endpoint.

### Схема на комуникацията

```text
Клиент → HTTP заявка → REST API / Сървър
Клиент ← HTTP отговор ← REST API / Сървър
```

Примерен ресурс в JSONPlaceholder:

```text
https://jsonplaceholder.typicode.com/posts
```

Този endpoint представя колекция от публикации (`posts`).

## 1.2. HTTP заявка

HTTP заявката съдържа най-често следните части:

```text
HTTP метод + URL + заглавки (headers) + тяло (body, при нужда)
```

Примерна заявка:

```text
POST /posts HTTP/1.1
Host: jsonplaceholder.typicode.com
Content-Type: application/json

{
  "title": "Моята публикация",
  "body": "Текст на публикацията",
  "userId": 1
}
```

- **HTTP методът** показва какво действие иска клиентът.
- **URL адресът** посочва ресурса.
- **Заглавките** описват допълнителна информация, например формат на данните.
- **Тялото** съдържа данни за изпращане, обикновено при `POST`, `PUT` или `PATCH`.

## 1.3. HTTP отговор

Сървърът връща отговор, който съдържа:

```text
Статус код + заглавки (headers) + тяло на отговора (body)
```

Пример:

```text
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{
  "userId": 1,
  "id": 1,
  "title": "...",
  "body": "..."
}
```

- **Статус кодът** показва дали заявката е успешна или има проблем.
- **Response headers** дават информация за типа съдържание, кеширане, сървър и други технически детайли.
- **Response body** съдържа върнатите данни — често в JSON формат.

# 2. URL адрес и ресурси

## 2.1. Структура на URL

Разгледайте адреса:

```text
https://jsonplaceholder.typicode.com/posts/1?userId=1
```

| Част | Значение |
|---|---|
| `https` | Протокол за защитена HTTP комуникация |
| `jsonplaceholder.typicode.com` | Домейн на сървъра |
| `/posts` | Endpoint за публикации |
| `/1` | Идентификатор на конкретна публикация |
| `?userId=1` | Query parameter — филтър или допълнителна настройка |

## 2.2. Path parameter и query parameter

**Path parameter** е част от пътя към конкретен ресурс:

```text
/posts/1
```

Тук `1` е идентификаторът на публикацията.

**Query parameter** се поставя след `?` и най-често филтрира, сортира или страницира резултатите:

```text
/posts?userId=1
```

Това търси публикациите на потребител с идентификатор `1`.

> **Добра практика:** Проверявайте внимателно endpoint, идентификатора и query параметрите. Малка грешка в адреса често води до `404 Not Found`.

# 3. HTTP методи и CRUD операции

CRUD е съкращение от четири основни действия върху данни:

- **Create** — създаване;
- **Read** — прочит;
- **Update** — обновяване;
- **Delete** — изтриване.

| CRUD операция | HTTP метод | Предназначение | Типичен endpoint |
|---|---|---|---|
| Create | `POST` | Създава нов ресурс | `/posts` |
| Read | `GET` | Връща ресурс или списък от ресурси | `/posts`, `/posts/1` |
| Update | `PUT` | Заменя или обновява съществуващ ресурс | `/posts/1` |
| Delete | `DELETE` | Изтрива ресурс | `/posts/1` |

## 3.1. GET — прочит на данни

`GET` се използва за получаване на данни. Обикновено не изпраща JSON тяло.

```bash
curl -i https://jsonplaceholder.typicode.com/posts/1
```

### Какво означават частите?

- `curl` е конзолен HTTP клиент;
- `-i` показва response headers заедно с response body;
- URL адресът сочи конкретната публикация с `id = 1`.

Очакван JSON отговор:

```json
{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit",
  "body": "quia et suscipit..."
}
```

За списък от публикации на определен потребител:

```bash
curl -i 'https://jsonplaceholder.typicode.com/posts?userId=1'
```

> **Внимание:** Ако URL адресът съдържа `?` или `&`, поставяйте го в единични кавички в терминал. Така shell програмата няма да интерпретира специалните символи.

## 3.2. POST — създаване на данни

`POST` изпраща данни към сървъра, за да създаде нов ресурс.

```bash
curl -i -X POST 'https://jsonplaceholder.typicode.com/posts' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Нов запис","body":"Тестово съдържание","userId":1}'
```

### Ключови редове

- `-X POST` задава HTTP метода;
- `-H 'Content-Type: application/json'` указва, че изпращаното тяло е JSON;
- `-d '...'` изпраща request body;
- `-i` показва статус реда и заглавките на отговора.

Очакваният статус е обикновено:

```text
HTTP/1.1 201 Created
```

JSONPlaceholder симулира създаването и връща обект с нов `id`.

## 3.3. PUT — обновяване на данни

`PUT` изпраща пълно представяне на ресурс, който трябва да бъде обновен. В много API-та се очаква да подадете всички важни полета на обекта.

```bash
curl -i -X PUT 'https://jsonplaceholder.typicode.com/posts/1' \
  -H 'Content-Type: application/json' \
  -d '{"id":1,"title":"Обновено заглавие","body":"Обновено съдържание","userId":1}'
```

### Какво да проверим?

- URL адресът съдържа идентификатора на ресурса: `/posts/1`;
- тялото е валиден JSON;
- `Content-Type` е `application/json`;
- отговорът има успешен статус, често `200 OK`.

> **Важно:** JSONPlaceholder е тестова услуга. `POST`, `PUT` и `DELETE` заявките изглеждат успешни, но не записват трайно промени в реална база данни.

## 3.4. DELETE — изтриване на данни

`DELETE` заявява изтриване на ресурс.

```bash
curl -i -X DELETE 'https://jsonplaceholder.typicode.com/posts/1'
```

При JSONPlaceholder отговорът обикновено е:

```text
HTTP/1.1 200 OK
```

В реален API може да получите и:

```text
HTTP/1.1 204 No Content
```

Код `204` означава: операцията е успешна, но сървърът няма данни за връщане в response body.

# 4. JSON — форматът за обмен на данни

**JSON** (_JavaScript Object Notation_) е текстов формат за представяне и обмен на структурирани данни.

## 4.1. Основни правила

- Данните се записват като двойки `ключ: стойност`;
- ключовете са в двойни кавички;
- текстовите стойности също са в двойни кавички;
- обектите са в `{ }`;
- масивите са в `[ ]`;
- елементите се разделят със запетая.

Пример за JSON обект:

```json
{
  "title": "Нов запис",
  "body": "Тестово съдържание",
  "userId": 1,
  "published": true
}
```

Пример за JSON масив:

```json
[
  {"id": 1, "title": "Първи запис"},
  {"id": 2, "title": "Втори запис"}
]
```

## 4.2. Невалиден JSON

Следният пример е невалиден:

```json
{
  'title': 'Нов запис',
  "userId": 1,
}
```

Проблеми:

1. JSON изисква **двойни**, а не единични кавички около ключовете и текстовите стойности.
2. Не се поставя запетая след последното поле.

Правилен вариант:

```json
{
  "title": "Нов запис",
  "userId": 1
}
```

# 5. Заглавки (HTTP headers)

HTTP заглавките пренасят метаданни за заявката или отговора.

## 5.1. Важни request headers

| Header | Значение | Пример |
|---|---|---|
| `Content-Type` | Формат на данните, които изпращаме | `application/json` |
| `Accept` | Форматът, който клиентът предпочита да получи | `application/json` |
| `Authorization` | Данни за удостоверяване | `Bearer <token>` |

Пример с два request headers:

```bash
curl -i 'https://jsonplaceholder.typicode.com/posts/1' \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer example-token'
```

JSONPlaceholder не изисква реален token за този endpoint. При реални защитени API-та липсващ, невалиден или изтекъл token често води до `401 Unauthorized`.

## 5.2. Важни response headers

| Header | Какво показва |
|---|---|
| `Content-Type` | Формата на върнатите данни |
| `Content-Length` | Размер на response body в байтове |
| `Cache-Control` | Правила за кеширане |
| `Date` | Време на генериране на отговора |

Проверявайте дали отговорът е JSON чрез header като:

```text
Content-Type: application/json; charset=utf-8
```

# 6. HTTP статус кодове

Статус кодът е първият важен знак дали заявката е успешна.

| Група | Значение | Примери |
|---|---|---|
| `2xx` | Успех | `200 OK`, `201 Created`, `204 No Content` |
| `4xx` | Проблем от страна на клиента | `400 Bad Request`, `401 Unauthorized`, `404 Not Found` |
| `5xx` | Проблем от страна на сървъра | `500 Internal Server Error` |

## 6.1. Най-често срещани кодове

### `200 OK`

Заявката е изпълнена успешно. Често се връща при `GET`, `PUT` и `DELETE`.

### `201 Created`

Създаден е нов ресурс. Често се връща след успешен `POST`.

### `204 No Content`

Операцията е успешна, но няма response body. Често се използва при `DELETE`.

### `400 Bad Request`

Сървърът не може да обработи заявката, защото има проблем в изпратените данни. Възможна причина: невалиден JSON или липсващо задължително поле.

### `401 Unauthorized`

Клиентът не е удостоверен. Възможни причини:

- липсва `Authorization` header;
- token-ът е невалиден;
- token-ът е изтекъл;
- използван е грешен тип удостоверяване.

**Следваща стъпка:** Проверете документацията на API-то и стойността на `Authorization` header. Уверете се, че token-ът е валиден и е изпратен в правилния формат.

### `404 Not Found`

Търсеният endpoint или ресурс не е намерен. Възможни причини:

- сгрешен URL адрес;
- грешно изписан endpoint;
- несъществуващ идентификатор;
- използван е грешен base URL или версия на API-то.

**Следваща стъпка:** Проверете домейна, endpoint-а, наклонените черти, идентификатора и документацията.

### `500 Internal Server Error`

На сървъра е възникнала неочаквана грешка. Възможни причини:

- грешка в сървърния код;
- проблем с база данни или външна услуга;
- временен проблем в инфраструктурата.

**Следваща стъпка:** Запишете URL, метод, headers, request body, статус и response body. Опитайте заявката отново по-късно и сигнализирайте на екипа, който поддържа API-то. Не приемайте автоматично, че проблемът е във вашия код.

# 7. Практически алгоритъм за анализ на заявка

При всяка заявка следвайте този ред:

1. **Проверете метода** — правилен ли е `GET`, `POST`, `PUT` или `DELETE`?
2. **Проверете URL адреса** — домейн, endpoint, `id`, query параметри.
3. **Проверете headers** — при JSON тяло има ли `Content-Type: application/json`?
4. **Проверете JSON тялото** — валиден ли е синтаксисът, има ли всички необходими полета?
5. **Прочетете статуса** — `2xx`, `4xx` или `5xx`?
6. **Прочетете response body** — има ли описание на грешка или върнати данни?
7. **Сравнете с документацията** — какво очаква API-то и какво реално сте изпратили?

## Пример за систематична проверка

Заявката връща `404 Not Found`:

```bash
curl -i 'https://jsonplaceholder.typicode.com/post/1'
```

Проверка:

1. Методът `GET` е подходящ.
2. В URL адреса endpoint-ът е `post`.
3. Документацията използва `posts`.
4. Поправяме адреса:

```bash
curl -i 'https://jsonplaceholder.typicode.com/posts/1'
```

Извод: проблемът е грешно изписан endpoint, а не липса на интернет или проблем със сървъра.

# 8. Внимание: чести грешки и добри практики

## Чести грешки

- Използване на `GET`, когато трябва да се създаде ресурс с `POST`.
- Липсващ `Content-Type: application/json` при изпращане на JSON тяло.
- Невалиден JSON: единични кавички, липсващи двойни кавички или излишна запетая.
- Изпращане на `PUT` към колекцията `/posts`, вместо към конкретен ресурс `/posts/1`.
- Приемане, че `200 OK` винаги означава, че данните са точно тези, които очакваме.
- Пренебрегване на response body и headers при грешка.
- Публикуване на реални пароли, API ключове или tokens в код, снимки или публични хранилища.

## Добри практики

- Използвайте `-i`, за да виждате статуса и response headers.
- При сложни заявки добавяйте данните постепенно: първо URL, после метод, headers и накрая body.
- Формулирайте ясно какъв резултат очаквате преди да изпратите заявката.
- При грешка записвайте: метод, URL, headers без тайни данни, request body, статус и response body.
- Четете документацията на API-то преди да предполагате имена на полета или endpoint-и.
- Не изпращайте чувствителни данни към непознати или тестови услуги.

# 9. Cheatsheet: речник и бърза справка

| Термин / синтаксис | Значение | Кратък пример |
|---|---|---|
| API | Интерфейс за комуникация между програми | `https://.../posts` |
| REST API | API, което работи с ресурси чрез HTTP | `/users/1` |
| Endpoint | Адрес на ресурс или операция в API | `/posts` |
| `GET` | Прочита данни | `curl -i '.../posts/1'` |
| `POST` | Създава нов ресурс | `curl -X POST ...` |
| `PUT` | Обновява ресурс | `curl -X PUT '.../posts/1' ...` |
| `DELETE` | Изтрива ресурс | `curl -X DELETE '.../posts/1'` |
| CRUD | Create, Read, Update, Delete | `POST`, `GET`, `PUT`, `DELETE` |
| Header | Метаданни към заявка или отговор | `Content-Type: application/json` |
| Request body | Данни, изпращани към сървъра | `-d '{"title":"..."}'` |
| JSON | Текстов формат за структурирани данни | `{"id":1,"title":"..."}` |
| `200 OK` | Успешна заявка | Успешен `GET` |
| `201 Created` | Създаден е ресурс | Успешен `POST` |
| `401 Unauthorized` | Липсва или е невалидно удостоверяване | Проверете `Authorization` |
| `404 Not Found` | Endpoint или ресурс не е намерен | Проверете URL адреса |
| `500 Internal Server Error` | Грешка от страна на сървъра | Запишете данните и опитайте по-късно |

# 11. Мини практически задачи

## Задача 1: Прочит и филтриране на данни

Изпълнете следните заявки и сравнете резултатите:

```bash
curl -i 'https://jsonplaceholder.typicode.com/posts/1'
```

```bash
curl -i 'https://jsonplaceholder.typicode.com/posts?userId=1'
```

**Насоки:**

1. При първата заявка определете дали отговорът е обект или масив.
2. При втората заявка пребройте колко публикации са върнати.
3. Посочете къде в URL адреса е посочен идентификатор и къде е филтърът.

## Задача 2: Създаване и обновяване на тестов ресурс

Изпратете `POST` заявка за нова публикация, след това изпратете `PUT` заявка към публикация с `id = 1`.

```bash
curl -i -X POST 'https://jsonplaceholder.typicode.com/posts' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Практикум по HTTP","body":"Създаване на тестов ресурс","userId":11}'
```

```bash
curl -i -X PUT 'https://jsonplaceholder.typicode.com/posts/1' \
  -H 'Content-Type: application/json' \
  -d '{"id":1,"title":"Обновен запис","body":"Тест за PUT заявка","userId":1}'
```

**Насоки:**

1. Запишете метода, URL адреса, request headers, request body и статус кода за всяка заявка.
2. Сравнете статусите и JSON отговорите.
3. Обяснете коя CRUD операция изпълнява всяка заявка.
4. Посочете защо промяната не е трайна при JSONPlaceholder.

## Финално обобщение

Успешната работа с REST API не е само изпращане на команда. Разработчикът анализира цялата комуникация: HTTP метода, URL адреса, headers, JSON данните, статус кода и отговора. Когато проверявате тези елементи систематично, откривате причината за повечето проблеми бързо и аргументирано.
