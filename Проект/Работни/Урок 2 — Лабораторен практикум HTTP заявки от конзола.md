**Предмет:** Интернет програмиране

**Специалност:** Приложно програмиране  
**Вид на занятието:** Упражнение  
**Тема от учебната програма:** Видове HTTP заявки — практическо лабораторно упражнение

---

## 1. Въведение: защо е важно?

Уеб приложенията постоянно обменят данни със сървъри: зареждат списък с продукти, създават поръчка, променят профил или изтриват запис. Когато изпращаме HTTP заявки от конзолата, виждаме директно какво изпраща клиентът и какво връща сървърът. Това е основно умение при разработка, тестване и отстраняване на проблеми в API.

### След този урок ще можете да:

- изпращате `GET`, `POST`, `PUT` и `DELETE` заявки към тестов REST API чрез `curl`;
- разчитате метод, URL, заглавки, JSON тяло, статус код и JSON отговор;
- свързвате HTTP методите с CRUD действията: Create, Read, Update и Delete;
- откривате вероятна причина и първа стъпка за проверка при `401`, `404` и `500`.

---

## 2. Необходими инструменти

За лабораторната работа са необходими:

- терминал: Windows Terminal, PowerShell, Command Prompt, Linux Terminal или терминалът във Visual Studio Code;
- конзолен HTTP клиент `curl`;
- интернет връзка;
- публичният тестов REST API **JSONPlaceholder**: `https://jsonplaceholder.typicode.com`.

> **Важно:** JSONPlaceholder е учебен тестов API. Заявките `POST`, `PUT` и `DELETE` връщат реалистични демонстрационни отговори, но обикновено не променят трайно данните на сървъра.

---

## 3. Основни понятия

### 3.1. Какво е HTTP заявка?

**HTTP заявка** е съобщение, което клиент изпраща до сървър. В тази лабораторна работа клиентът е програмата `curl`, а сървърът е JSONPlaceholder.

Текстова схема:

```text
Терминал + curl  →  HTTP заявка  →  REST API сървър
Терминал + curl  ← HTTP отговор  ← REST API сървър
```

### 3.2. Основни части на заявката

| Част | Значение | Пример |
|---|---|---|
| HTTP метод | Показва желаното действие | `GET`, `POST`, `PUT`, `DELETE` |
| URL | Адрес на ресурса | `https://jsonplaceholder.typicode.com/posts/1` |
| Заглавки | Допълнителна информация за заявката | `Content-Type: application/json` |
| Тяло на заявката | Данни, изпращани към сървъра | `{"title":"Нова публикация"}` |

### 3.3. Какво съдържа HTTP отговорът?

Сървърът обикновено връща:

1. **Статус код** — дали обработката е успешна или има грешка;
2. **Заглавки на отговора** — например формат на върнатите данни;
3. **Тяло на отговора** — често JSON с резултатни данни.

Примерна схема:

```text
HTTP/1.1 200 OK                 ← статусен ред
Content-Type: application/json  ← заглавка

{                               ← JSON тяло
  "id": 1,
  "title": "..."
}
```

## 4. CRUD и HTTP методи

CRUD описва четири основни операции с данни.

| CRUD операция | Предназначение | Типичен HTTP метод | Примерен URL |
|---|---|---|---|
| Create | Създава нов ресурс | `POST` | `/posts` |
| Read | Получава данни | `GET` | `/posts/1` |
| Update | Променя съществуващ ресурс | `PUT` | `/posts/1` |
| Delete | Изтрива ресурс | `DELETE` | `/posts/1` |

> **Правило за запомняне:** Методът показва какво искаме да направим, а статус кодът показва как е приключила обработката.

### `GET` — получаване на данни

Използва се за четене на списък или единичен ресурс. Обикновено няма тяло на заявката.

```bash
curl -i https://jsonplaceholder.typicode.com/posts/1
```

- `curl` стартира конзолния HTTP клиент;
- `-i` показва и заглавките на HTTP отговора;
- URL адресът посочва публикация с идентификатор `1`;
- без `-X` по подразбиране се изпраща `GET` заявка.

Очакван резултат: статус `200 OK` и JSON данни за публикацията.

### `POST` — създаване на нов ресурс

Използва се за изпращане на нови данни към сървъра. При JSON тяло е необходима заглавка `Content-Type: application/json`.

```bash
curl -i -X POST https://jsonplaceholder.typicode.com/posts \
  -H "Content-Type: application/json" \
  -d '{"title":"HTTP лаборатория","body":"Пробна публикация","userId":1}'
```

- `-X POST` задава HTTP метода;
- `-H` добавя заглавка; тук тя казва, че тялото е JSON;
- `-d` изпраща данните в тялото на заявката;
- `201 Created` е типичен успешен статус при създаден ресурс.

### `PUT` — пълна промяна на ресурс

`PUT` обикновено изпраща пълно ново представяне на ресурс. В реален API често трябва да включим всички задължителни полета.

```bash
curl -i -X PUT https://jsonplaceholder.typicode.com/posts/1 \
  -H "Content-Type: application/json" \
  -d '{"id":1,"title":"Обновено заглавие","body":"Обновено съдържание","userId":1}'
```

- URL завършва с `/1`, защото променяме ресурс с идентификатор `1`;
- JSON тялото съдържа обновените данни;
- при успешна промяна често се връща `200 OK`.

### `DELETE` — изтриване на ресурс

Използва се за премахване на ресурс.

```bash
curl -i -X DELETE https://jsonplaceholder.typicode.com/posts/1
```

- `-X DELETE` задава операцията по изтриване;
- URL посочва ресурса, който трябва да бъде изтрит;
- заявката обичайно няма тяло;
- API може да върне `200 OK`, `204 No Content` или друг успешен статус според своята документация.

## 5. Полезни параметри на `curl`

| Параметър | Значение | Пример |
|---|---|---|
| `-i` | Показва заглавките и тялото на отговора | `curl -i URL` |
| `-X` | Задава HTTP метод | `-X POST` |
| `-H` | Добавя HTTP заглавка | `-H "Content-Type: application/json"` |
| `-d` | Изпраща тяло на заявката | `-d '{"name":"Ana"}'` |
| `-v` | Подробна диагностична информация | `curl -v URL` |

> В Windows PowerShell понякога `curl` има различно поведение. Ако е необходимо, използвайте `curl.exe` вместо `curl`, например `curl.exe -i https://jsonplaceholder.typicode.com/posts/1`.

## 6. Анализ на JSON отговор

Примерен отговор от `GET /posts/1`:

```json
{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit",
  "body": "quia et suscipit..."
}
```

Как да го разчетем:

- JSON е текстов формат за структурирани данни;
- данните са записани като двойки **ключ: стойност**;
- `id` е идентификаторът на публикацията;
- `userId` показва свързан потребител;
- `title` и `body` са съдържателни полета на ресурса.

### Алгоритъм за анализ на всяка заявка

1. Определи **метода**: `GET`, `POST`, `PUT` или `DELETE`.
2. Прочети **URL**: кой ресурс и кой идентификатор се използват?
3. Провери **заглавките**: има ли `Content-Type: application/json` при изпращане на JSON?
4. Провери **тялото**: валиден ли е JSON текстът?
5. Прочети **статус кода**.
6. Анализирай **JSON отговора**: какви данни са върнати?
7. Сравни резултата с очакваното действие.

## 7. Статус кодове и дебъгване

| Статус | Значение | Вероятна причина | Първа стъпка за проверка |
|---|---|---|---|
| `200 OK` | Заявката е успешна | Няма проблем | Прочети JSON отговора |
| `201 Created` | Създаден е нов ресурс | Няма проблем | Провери върнатия идентификатор |
| `401 Unauthorized` | Липсва или е невалидно удостоверяване | API изисква токен/ключ/вход | Провери документацията и заглавката `Authorization` |
| `404 Not Found` | Ресурсът или адресът не е намерен | Грешен URL, ресурс или идентификатор | Провери пътя и идентификатора |
| `500 Internal Server Error` | Вътрешна грешка на сървъра | Проблем в сървърното приложение или услуга | Провери валидността на заявката и опитай отново по-късно |

### Стратегия за дебъгване

```text
1. Прочети статус кода.
2. Провери URL и идентификатора.
3. Провери HTTP метода.
4. При POST/PUT провери Content-Type и JSON тялото.
5. При 401 провери документацията за Authorization.
6. При 500 запази заявката и отговора, след което провери дали грешката се повтаря.
```

## 8. Внимание: чести грешки и добри практики

### Чести грешки

- Използване на `GET`, когато целта е създаване или изтриване на данни.
- Изпращане на JSON с `POST` или `PUT`, но без `Content-Type: application/json`.
- Невалиден JSON: липсващи двойни кавички около ключове и текстови стойности, излишна запетая или неправилно затворени скоби.
- Грешен URL: например `/post/1` вместо `/posts/1`.
- Объркване между `401` и `404`: `401` е проблем с удостоверяването, а `404` означава липсващ адрес или ресурс.
- Приемане, че `500` винаги е причинен от клиента. Този статус обикновено показва проблем в сървъра, но валидността на заявката все пак трябва да се провери.

### Добри практики

- Използвайте `-i`, когато учите или дебъгвате, за да виждате статуса и заглавките.
- Изграждайте заявката в ред: **метод → URL → заглавки → тяло → анализ на отговора**.
- Копирайте точния URL от документацията на API, вместо да го пишете по памет.
- Записвайте изпратената команда, статуса и кратък извод в лабораторния протокол.
- Не поставяйте реални пароли, API ключове или токени в команди, екранни снимки и споделени файлове.
- Четете документацията на конкретния API: успешните статуси и полетата могат да се различават между услугите.

## 9. Cheatsheet: бърза справка

| Термин / синтаксис | Значение | Кратък пример |
|---|---|---|
| `GET` | Получава данни | `curl -i https://.../posts/1` |
| `POST` | Създава нов ресурс | `curl -i -X POST URL -d 'JSON'` |
| `PUT` | Заменя/обновява ресурс | `curl -i -X PUT URL/1 -d 'JSON'` |
| `DELETE` | Изтрива ресурс | `curl -i -X DELETE URL/1` |
| `-i` | Показва отговорни заглавки | `curl -i URL` |
| `-H` | Добавя заглавка | `-H "Content-Type: application/json"` |
| `-d` | Изпраща тяло | `-d '{"completed":true}'` |
| JSON | Формат за структурирани данни | `{"id":1,"title":"Задача"}` |
| `200 OK` | Успешно изпълнение | Получени данни при GET |
| `201 Created` | Успешно създаване | Нов ресурс след POST |
| `401 Unauthorized` | Липсва/не е валидно удостоверяване | Провери `Authorization` |
| `404 Not Found` | Ресурсът липсва | Провери URL и `id` |
| `500 Internal Server Error` | Сървърна грешка | Провери заявката и услугата |

## 10. Въпроси за самопроверка

1. Каква е основната разлика между `GET` и `POST`?
2. Защо при изпращане на JSON с `POST` или `PUT` използваме заглавката `Content-Type: application/json`?
3. Какво означава `404 Not Found` и коя е първата ти проверка?
4. Защо не трябва да използваме `GET` за изтриване на ресурс?

### Кратък ключ за проверка

1. `GET` получава данни, а `POST` обикновено изпраща данни за създаване на нов ресурс.
2. Тя указва на сървъра, че тялото на заявката е във формат JSON.
3. Адресът или ресурсът не е намерен; проверяват се URL и идентификаторът.
4. `GET` е предназначен за четене и не трябва да променя състоянието на системата.

## 11. Мини практически задачи

### Задача 1: Прочети и анализирай ресурс

Изпълни:

```bash
curl -i https://jsonplaceholder.typicode.com/todos/1
```

Отговори:

1. Кой HTTP метод е изпратен?
2. Какъв статус код получаваш?
3. Кои са трите ключа в JSON обекта?
4. Каква е стойността на полето `completed`?

**Насока:** Ако не виждаш статуса и заглавките, провери дали си използвал параметъра `-i`.

### Задача 2: Създай и промени демонстрационна задача

1. Изпрати `POST` заявка към `https://jsonplaceholder.typicode.com/todos` със следното тяло:

```json
{
  "userId": 12,
  "title": "Подготовка за практикум",
  "completed": false
}
```

2. Изпрати `PUT` заявка към `https://jsonplaceholder.typicode.com/todos/1`, с която променяш задачата на завършена.
3. Запиши за всяка заявка: метода, URL, заглавките, тялото и статуса.

**Насока:** Използвай шаблона `curl -i -X МЕТОД URL -H "Content-Type: application/json" -d 'JSON'`.

## 12. Финално обобщение

При работа с REST API мисли последователно:

```text
Какво искам да направя?
        ↓
Кой HTTP метод отговаря на действието?
        ↓
Кой е точният URL?
        ↓
Нужни ли са заглавки и JSON тяло?
        ↓
Какъв статус и какъв JSON отговор получавам?
        ↓
Ако има грешка — какво проверявам първо?
```

**Ключова идея:** Уверената работа с HTTP не означава запаметяване на всички кодове и правила. Означава да умееш да изпратиш ясна заявка, да прочетеш отговора и да направиш логична следваща проверка при проблем.
