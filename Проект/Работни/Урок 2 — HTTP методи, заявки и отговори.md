## Въведение

# 1. Какво е HTTP?

**HTTP** идва от _HyperText Transfer Protocol_. Това е набор от правила за комуникация между:

- **клиент** — най-често браузър, мобилно приложение или JavaScript код;
- **сървър** — приложение, което обработва заявките и връща данни.

Основният модел е:

```text
Клиент → HTTP заявка → Сървър → HTTP отговор → Клиент
```

Пример:

```text
Браузърът иска списък с книги.
↓
Изпраща GET /api/books
↓
Сървърът намира книгите.
↓
Връща 200 OK и данните в JSON формат.
```

> **Важно:** Не е необходимо да запаметявате цялата HTTP спецификация. Важно е да разбирате какво действие се извършва, какъв метод е подходящ и какво означава отговорът на сървъра.

# 2. HTTP заявка: основни части

HTTP заявката е съобщение от клиента към сървъра. Най-често съдържа следните части:

| Част | Значение | Пример |
|---|---|---|
| Метод | Какво действие иска клиентът | `GET`, `POST`, `PATCH` |
| URL | Адресът на ресурса | `/api/books/12` |
| Заглавки | Допълнителна информация | `Content-Type: application/json` |
| Тяло | Данни, които се изпращат | JSON с нова книга |

## 2.1. Опростена GET заявка

```http
GET /api/books/12 HTTP/1.1
Host: school-library.example
Accept: application/json
```

Разчитане:

- `GET` — искаме да получим информация;
- `/api/books/12` — искаме книгата с идентификатор `12`;
- `Accept: application/json` — клиентът очаква данните да бъдат в JSON формат;
- при `GET` обикновено **няма тяло на заявката**.

## 2.2. Опростена POST заявка

```http
POST /api/books HTTP/1.1
Host: school-library.example
Content-Type: application/json

{
  "title": "Под игото",
  "author": "Иван Вазов"
}
```

Разчитане:

- `POST` — изпращаме данни с цел създаване на нов ресурс;
- `/api/books` — работим с колекцията от книги;
- `Content-Type: application/json` — тялото е JSON;
- след празния ред е разположено **тялото на заявката**.

# 3. HTTP методи и CRUD операции

**CRUD** е съкращение от четири основни операции с данни:

| CRUD операция | Значение | Подходящ HTTP метод |
|---|---|---|
| Create | Създаване | `POST` |
| Read | Прочитане / получаване | `GET` |
| Update | Промяна | `PUT` или `PATCH` |
| Delete | Изтриване | `DELETE` |

## 3.1. GET — получаване на данни

Използваме `GET`, когато искаме да прочетем данни, без да променяме ресурса на сървъра.

```http
GET /api/products HTTP/1.1
```

Възможни приложения:

- списък с продукти;
- профил на потребител;
- подробности за една публикация;
- търсене чрез параметри в URL.

Пример с параметър:

```http
GET /api/products?category=laptops HTTP/1.1
```

Тук `category=laptops` е параметър за филтриране.

## 3.2. POST — създаване на нов ресурс

Използваме `POST`, когато изпращаме нови данни към сървъра. Често това означава създаване на ресурс.

```http
POST /api/tasks HTTP/1.1
Content-Type: application/json

{
  "text": "Подготовка за контролно",
  "status": "new"
}
```

Възможни приложения:

- създаване на потребител;
- добавяне на продукт;
- публикуване на коментар;
- създаване на задача.

## 3.3. PUT — пълна замяна на ресурс

`PUT` се използва, когато изпращаме цялото ново състояние на съществуващ ресурс.

```http
PUT /api/users/8 HTTP/1.1
Content-Type: application/json

{
  "name": "Мария Иванова",
  "email": "maria@example.com",
  "role": "student"
}
```

> При `PUT` мислим за **пълна замяна**: изпращаме всички важни данни за ресурса.

## 3.4. PATCH — частична промяна на ресурс

`PATCH` се използва, когато променяме само част от ресурса.

```http
PATCH /api/tasks/15 HTTP/1.1
Content-Type: application/json

{
  "status": "done"
}
```

Тук се променя само свойството `status` на задача с идентификатор `15`.

> **Правило:** Ако променяме само едно или няколко полета, обикновено използваме `PATCH`.

## 3.5. DELETE — изтриване на ресурс

`DELETE` се използва за премахване на ресурс.

```http
DELETE /api/tasks/15 HTTP/1.1
```

Пример: изтриване на задача с идентификатор `15`.

# 4. HTTP отговори и статус кодове

След като сървърът обработи заявката, той изпраща **HTTP отговор**. Отговорът съдържа:

- статус код;
- кратко текстово описание на статуса;
- заглавки;
- по избор — тяло с данни или описание на грешка.

## 4.1. Пример за успешен отговор

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 12,
  "title": "Малкият принц"
}
```

Разчитане:

- `200 OK` — заявката е изпълнена успешно;
- `Content-Type: application/json` — върнатите данни са JSON;
- тялото съдържа данните за книгата.

## 4.2. Основни статус кодове

| Статус | Име | Значение | Типичен пример |
|---|---|---|---|
| `200` | OK | Операцията е успешна | Получен е списък със задачи |
| `201` | Created | Създаден е нов ресурс | Добавена е нова книга |
| `400` | Bad Request | Заявката съдържа невалидни или липсващи данни | Липсва поле `title` |
| `403` | Forbidden | Клиентът няма право за действието | Ученик се опитва да изтрие чужда задача |
| `404` | Not Found | Търсеният ресурс не съществува | Няма книга с ID `99` |
| `500` | Internal Server Error | Неочаквана грешка на сървъра | Грешка в сървърния код или база данни |

## 4.3. Пример за отговор при успешно създаване

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 25,
  "title": "Под игото",
  "author": "Иван Вазов"
}
```

Статусът `201 Created` показва, че сървърът е създал нов ресурс.

## 4.4. Пример за отговор при грешка

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "message": "Книгата не е намерена."
}
```

Статусът `404 Not Found` означава, че адресът може да е валиден, но ресурсът с този идентификатор липсва.

---

# 5. Заглавки и тяло на заявката

## 5.1. Какво са HTTP заглавките?

**HTTP заглавките** са редове с допълнителна информация за заявката или отговора.

Често използвани заглавки:

| Заглавка | Значение |
|---|---|
| `Content-Type` | Форматът на данните, които изпращаме |
| `Accept` | Форматът на данните, които клиентът очаква |
| `Authorization` | Данни за удостоверяване и права за достъп |

Пример:

```http
Content-Type: application/json
```

Това означава: „Изпращам данни във формат JSON“.

## 5.2. Какво е тяло на заявката?

**Тялото** съдържа данните, които клиентът изпраща към сървъра. Най-често се използва при `POST`, `PUT` и `PATCH`.

```json
{
  "title": "Интернет програмиране",
  "author": "Учебен екип"
}
```

При `GET` и `DELETE` обикновено не изпращаме тяло.

# 6. Практика с JavaScript fetch()

Методът `fetch()` позволява на JavaScript кода в браузъра да изпраща HTTP заявки.

## 6.1. GET заявка с fetch()

```javascript
async function loadPosts() {
  // Изпращаме GET заявка към публичен тестов API.
  const response = await fetch(
    'https://jsonplaceholder.typicode.com/posts?_limit=3'
  );

  // Проверяваме дали отговорът е успешен.
  if (!response.ok) {
    throw new Error('Грешка. Статус: ' + response.status);
  }

  // Преобразуваме JSON отговора в JavaScript стойност.
  const posts = await response.json();

  console.log(posts);
}

loadPosts();
```

### Какво прави кодът?

1. `fetch(...)` изпраща заявка. Ако не посочим метод, по подразбиране се използва `GET`.
2. `await` изчаква отговора от сървъра.
3. `response.ok` е `true` при успешен статус от `200` до `299`.
4. `response.status` съдържа числовия статус код.
5. `response.json()` прочита JSON тялото на отговора.

## 6.2. POST заявка с fetch()

```javascript
async function createPost() {
  const newPost = {
    title: 'HTTP упражнение',
    body: 'Изпращам JSON тяло чрез POST.',
    userId: 1
  };

  const response = await fetch(
    'https://jsonplaceholder.typicode.com/posts',
    {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json'
      },
      body: JSON.stringify(newPost)
    }
  );

  if (response.status === 201) {
    const createdPost = await response.json();
    console.log('Създаден ресурс:', createdPost);
  } else {
    console.log('Неуспешно създаване. Статус:', response.status);
  }
}

createPost();
```

### Ключови редове

| Код | Обяснение |
|---|---|
| `method: 'POST'` | Посочва, че създаваме ресурс |
| `Content-Type: 'application/json'` | Указва, че изпращаме JSON |
| `JSON.stringify(newPost)` | Превръща JavaScript обекта в JSON текст |
| `response.status === 201` | Проверява дали ресурсът е създаден успешно |

## 6.3. PATCH заявка с fetch()

```javascript
async function completeTask() {
  const response = await fetch('/api/tasks/15', {
    method: 'PATCH',
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      status: 'done'
    })
  });

  if (response.ok) {
    console.log('Задачата е отбелязана като завършена.');
  }
}
```

Тази заявка променя само статуса на задача с ID `15`.

# 7. Внимание: чести грешки и добри практики

## Чести грешки

- **Използване на `GET` за промяна или изтриване на данни.** `GET` е предназначен за получаване на данни.
- **Използване на `200` при създаване на нов ресурс.** При успешно създаване обичайният избор е `201 Created`.
- **Липсваща заглавка `Content-Type` при изпращане на JSON.** Сървърът може да не разпознае правилно данните.
- **Изпращане на JavaScript обект директно като `body`.** При JSON трябва да използваме `JSON.stringify()`.
- **Бъркане между `403` и `404`.** `403` означава „нямаш право“, а `404` означава „не е намерено“.
- **Приемане, че всяка заявка е успешна.** Винаги проверявайте `response.ok` или `response.status`.

## Добри практики

- Избирайте метод според действието: четене, създаване, промяна или изтриване.
- Използвайте ясни URL адреси, например `/api/books/12`.
- Изпращайте JSON с `Content-Type: application/json`.
- Проверявайте статуса на отговора и обработвайте грешките.
- Не показвайте технически данни за грешка директно на крайния потребител.
- За частична промяна предпочитайте `PATCH`, а за пълна замяна — `PUT`.

# 8. Cheatsheet: бърз справочник

| Термин / синтаксис | Значение | Кратък пример |
|---|---|---|
| `GET` | Получава данни | `GET /api/books` |
| `POST` | Създава ресурс или изпраща нови данни | `POST /api/books` |
| `PUT` | Заменя целия ресурс | `PUT /api/users/8` |
| `PATCH` | Променя част от ресурс | `PATCH /api/tasks/15` |
| `DELETE` | Изтрива ресурс | `DELETE /api/tasks/15` |
| CRUD | Create, Read, Update, Delete | `POST`, `GET`, `PATCH`, `DELETE` |
| URL | Адрес на ресурс | `/api/products/3` |
| Header | Допълнителна информация | `Content-Type: application/json` |
| Request body | Данни в заявката | `{ "name": "Анна" }` |
| `200 OK` | Успешно изпълнение | Получен е списък |
| `201 Created` | Създаден е нов ресурс | Добавена е задача |
| `400 Bad Request` | Невалидни или непълни данни | Липсва `title` |
| `403 Forbidden` | Няма право за операцията | Забранено изтриване |
| `404 Not Found` | Ресурсът не съществува | Няма потребител с ID `99` |
| `500 Internal Server Error` | Грешка на сървъра | Неочаквана вътрешна грешка |
| `fetch()` | Изпраща HTTP заявка от JavaScript | `fetch('/api/books')` |
| `response.ok` | Проверява дали отговорът е успешен | `if (response.ok) { ... }` |

# 9. Въпроси за самопроверка

1. Каква е основната разлика между `GET` и `POST`?
2. Кой HTTP метод бихте използвали, за да промените само имейла на потребител?
3. Какво означава статус код `404`?
4. Кога е подходящо да използваме статус `201 Created`?

## Верни насоки за отговор

1. `GET` получава данни, а `POST` най-често изпраща нови данни за създаване на ресурс.
2. `PATCH`, защото се променя само едно поле.
3. Търсеният ресурс не е намерен.
4. След успешно създаване на нов ресурс, например нова задача или нова книга.

# 10. Мини задачи за упражнение

### Насоки

- Разпознайте CRUD операцията.
- Изберете метода.
- Помислете дали резултатът е успешен, липсващ ресурс или липса на права.

## Задача 2: Напишете POST заявка с fetch()

Напишете JavaScript код, който изпраща нова задача към `/api/tasks`.

Данните за задачата са:

```json
{
  "text": "Преговор на HTTP методи",
  "status": "new"
}
```

### Насоки

- Използвайте `fetch()`.
- Посочете `method: 'POST'`.
- Добавете заглавка `Content-Type: application/json`.
- Използвайте `JSON.stringify()` за тялото.
- Проверете дали отговорът е със статус `201`.
